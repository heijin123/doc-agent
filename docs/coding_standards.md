# doc-agent 开发守则（用户硬性标准 · 八条）

> 生效：2026-09-07（用户口述，写代码前立规）。M1-M4 全程强制，review 时逐条对照。
> 分工：**黑镜写代码实现，用户做框架设计与规划**（需求范围/架构形态/验收标准由用户拍板）。
> 版本：v1.1（2026-09-07 补充标准三~八：拆分大函数/嵌套层级/注释取舍/硬编码常量/拒绝炫技/模块化）

## 标准一：不要过度设计

- 只写**当前需求需要的最小结构**；不为"未来可能"预建抽象层、可配置项、接口壳。
- 需求真正出现时再重构，不提前绕远（YAGNI）。
- 能用一个函数解决的，不拆模块；能直写的，不加状态机/工厂/装饰器。
- 判断句：这个抽象今天有第二个使用方吗？没有就不建。

## 标准二：变量命名向人类语言靠拢

- 变量/函数/类名 = 读起来像一句自然语言，语义自解释。
- 全名、不缩写、不用拼音缩写/单字母（循环变量除外）。
  - ✅ `documents_that_failed_to_parse`、`is_quality_gate_passed`、`page_has_searchable_text`
  - ❌ `bad_docs`、`qg_pass`、`txt_ok`
- 长度服从清晰度——名字长一点没关系，读者不用查注释。
- 中文注释只讲 **why**（为什么这么写），不重复 what（代码本身已可读）。

## 标准三：拆分大函数

- 函数体超过 **~50 行** 或承担 **≥2 个职责**（读完要分段想"这一步在干嘛"）→ 拆。
- 拆法：按职责抽私有子函数（`_xxx`），主函数变成"步骤清单"，读主函数就能看到全貌。
- 判断信号：写完发现需要加"段落注释"才能看懂分段——这就是该拆的信号；分段注释删掉、换成子函数名。
- 例外：纯顺序的短数据处理、装饰器包装等"拆了更碎"的场景不强拆。

## 标准四：控制嵌套层级

- 缩进嵌套 **≤ 3 层**（if/for/try 叠 4 层及以上 = 必须重构）。
- 超限时优先 **早退（guard clause）**——先处理异常/边界再写主逻辑：
  - ❌ 包 4 层 if 判空判权限再执行
  - ✅ 开头 `if not xxx: return/raise`，主逻辑留在平层
- 循环内继续加 if 的，考虑提成"判断函数"（`should_skip(chunk)`）让循环体变平。
- 判据：一个函数最深处缩进超过 3 个 Tab/空格层级 = 敲响警钟。

## 标准五：注释取舍（与标准二末条同源，单列强调）

**写**（why 类，代码看不出来的）：
- 业务规则与背景（"超 15 天订单必须转人工，平台政策"）
- 踩坑决策（"这里不能直接用 X，因为…"）
- 非显然的权衡（"用滑窗切块是有意为之，屏蔽变量"）
- 对外契约前提（参数语义、返回值约定）

**不写**（what 类，代码已经说清楚的）：
- 逐行翻译式注释（`# 打开文件` `# 遍历列表`）——删掉
- 显而易见的逻辑说明
- 与代码脱节的陈旧注释（改代码必须同步改注释，否则删注释）

判据：注释能回答"为什么/为什么不是另一种写法"就留；只复述代码的就删。

## 标准六：提取硬编码常量

- 魔法数字/字符串（阈值、超时、大小上限、状态名）**出现 ≥2 次或承载业务含义** → 模块顶部命名常量。
  - ✅ `MIN_TEXT_CHARS_PER_PAGE = 80`、`QUALITY_GATE_RED_CHARS = 20`
  - ❌ 函数里散落 `if chars < 80`、`timeout=30`
- 同模块多个常量按语义分组放模块顶部常量区；跨模块共享的放一个 `settings.py`/`constants.py`。
- 例外：字面量本身就是全部语义且只用一次（如 `page + 1`），不必提取。
- 改动收益：调阈值只改一处，review 时一眼看到全部可调参数。

## 标准七：拒绝过度炫技

- 可读性 > 行数少 > "看起来厉害"。**一行流 / 复杂推导式 / 装饰器链 / 元编程 / 重载运算符** 一律先写平实版。
- 只有在**性能实测有据**（profile 数据说话）时才用技巧，且必须加注释说明为什么必须这样写。
- 不引入"为了用而用"的库/语法特性（如 lambda 嵌套、functools 花活）。
- 判据：这段代码让 3 天后的自己/结对伙伴一眼能懂吗？要停下来想 10 秒以上的写法 = 炫技，重写。

## 标准八：模块化

- **文件职责单一**：一个文件讲一件事（解析、切块、检索、API 各归各），文件名 = 职责名。
- **依赖单向**：按层组织，低层不 import 高层（ingest 不 import api；vectorstore 不 import ingest）。
- 函数间靠**参数与返回值**协作，不靠模块级可变状态互相暗连（全局变量跨函数改 = 拆信号）。
- 模块内公开面最小：能 `_` 私有就不导出；import 时用全路径包名，不 `from x import *`。
- 判据：改一个需求时，只动一个文件 = 模块化合格；要连带改 3 个文件且都在 import 链条上绕 = 分层有问题。

## 生效与复查

- 以上八条 M1-M4 全程强制；review（结对 review）时逐条对照，违反即改。
- 冲突时优先级：**可读性 > 简洁 > 技巧**；标准之间打架时（如"不过度设计" vs "模块化"），按当前需求的实际复杂度裁量，并在代码注释里写明取舍理由。
